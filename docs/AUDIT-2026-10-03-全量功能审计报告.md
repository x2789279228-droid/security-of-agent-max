## 0. 执行摘要

### 0.1 总体判断

这个平台的**架构纵深是真实的**，不是 PPT 纵深。以下设计经审计确认成立：

- 响应引擎 9 层安全检查链（Grounding 门控 → 命令白名单 → 参数强校验 → 资产白名单 → 幂等 → 执行模式 → 最小权限 → 执行后验证 → TTL 解封）**真实存在且默认拒绝**
- `veto_gates.apply_confirmation_gate` 用**程序化信号**（非 LLM 判断）保证 `confirmed` 结论在缺少非 LLM 检测器证据时结构性不可达
- Agent 轮次循环**有界**（`for round_num in range(1, max_rounds+1)` + hop 预算 + 提前 break），全链路无无界递归
- 命令白名单（`command_whitelist.py`）使用**锚定正则 + 全局注入黑名单 + 默认拒绝**，是全项目最干净的组件之一
- CI 真实有效：Trivy 扫描、前端 lint+build、Flink 编译、API 冒烟、覆盖率门禁

但**安全承诺与实现之间存在系统性落差**，核心是三类：

1. **"默认拒绝"的默认值反了** —— 密钥、HMAC、执行模式、预算、角色校验，凡是能写死的地方默认值都是最危险的那个
2. **守卫的信任边界在 API 层被绕过** —— MCP Guard / SecurityGuard / 审计门控内部实现正确，但调用它们的 HTTP 端点把**身份字段交给了客户端**（`user_role`、`caller`、`grounding_score`）
3. **"永不丢事件"的承诺在故障路径上不成立** —— P0 队列的 pop 非原子、本地 deque 静默淘汰、Temporal 重复提交导致双重审计

### P0-1 · 命令执行通道的 SSH 主机密钥完全不校验

**位置**：`backend/response_engine/ssh_firewall.py:167`、`backend/response_engine/transport.py:181-199`

```python
# ssh_firewall.py:167 —— 无条件接受任意主机密钥
client.load_system_host_keys()
client.set_missing_host_key_policy(paramiko.AutoAddPolicy())
```
```python
# transport.py:181-194 —— known_hosts 缺失时退化为 /dev/null，等于关闭校验
known_hosts_candidates = ["/tmp/ssh/known_hosts", "/dev/null"]
ssh_args = ["ssh", "-o", "StrictHostKeyChecking=accept-new", "-o", f"UserKnownHostsFile={known_hosts}", ...]
```

**影响**：这是**全场风险最高的一条**。该通道执行 `sudo iptables`（`use_sudo=True`）、`netsh advfirewall`、`pkill`、写 `/etc/hosts`，目标默认是 `host.docker.internal` 的 `Admin` 账户。任何能做 DNS 劫持或 ARP 欺骗的攻击者，可以透明 MITM 这条通道，**在安全设备自己不知道的情况下向内网主机下发任意 iptables/netsh 命令**。`AutoAddPolicy` 会把伪造密钥自动写入 known_hosts，攻击持续有效。

`transport.py` 的回退更糟：`/tmp/ssh/known_hosts` 不存在时静默使用 `/dev/null`，而 entrypoint 只有在密钥挂载成功时才创建该文件（`entrypoint.sh:29-43`，缺失时走 stub 分支）—— 也就是**降级路径恰好是校验关闭的路径**。

**修复**：
```python
# ssh_firewall.py
client.load_system_host_keys("/tmp/ssh/known_hosts")
client.set_missing_host_key_policy(paramiko.RejectPolicy())   # 未知主机直接拒绝
```
```python
# transport.py —— 删除 /dev/null 回退，缺失即启动失败
if not os.path.isfile(known_hosts):
    raise RuntimeError("known_hosts 缺失，拒绝以关闭主机校验的方式连接响应目标")
ssh_args = ["ssh", "-o", "StrictHostKeyChecking=yes", ...]
```
同时在 entrypoint 中 `known_hosts` 缺失时**直接 exit 1**，不要降级 stub。

### P0-2 · 响应策略的 severity 阈值被 fail-open 绕过

**位置**：`backend/response_engine/response_policies.py:83-92`

```python
severity_order = ["info", "low", "medium", "high", "critical"]
try:
    if severity_order.index(severity) < severity_order.index(self.min_severity):
        return False
except ValueError:
    pass            # ← 未知 severity 落到这里
return True         # ← 默认放行
```

**影响**：任何不在 `severity_order` 里的 severity 值都会**跳过整个阈值判断直接放行**。可触发路径：

- LLM 幻觉产出 `severity="unknown"` / `"Critical"`（大小写不同 → `list.index` 抛 ValueError）
- 上游字段缺失时 `severity` 传空串
- `/api/response/simulate` 的 `severity` 是**客户端自由字符串**（`routers/response.py:118`）

配置了 `min_severity: high` 的封禁策略，会被 `severity="unknown"` 的事件触发。`matches()` 对 `threat_type` 做了 `.upper()` 归一（`response_policies.py:115`），**唯独漏了 severity** —— 这是一个明确的归一化遗漏，不是设计意图。

> 该项为 2026-09-01 审计 CRIT-03，**至今未修复**。

**修复**：
```python
SEVERITY_ALIASES = {"informational": "info", "crit": "critical", "medium-high": "high"}

def _passes_thresholds(self, confidence: float, severity: str) -> bool:
    if confidence < self.min_confidence:
        return False
    sev = SEVERITY_ALIASES.get(str(severity or "").strip().lower(), str(severity or "").strip().lower())
    if sev not in severity_order:
        return False                    # 未知 severity → 拒绝，不是放行
    return severity_order.index(sev) >= severity_order.index(self.min_severity)
```
补一条单测：`severity="unknown"` + `min_severity="critical"` 必须 `matches() == False`。

### P0-6 · 硬编码 HMAC 兜底密钥使审批签名与审计哈希链可伪造

**位置**：`backend/security_crypto.py:24-28`；`config.py:60,235`

```python
def hmac_hex(message, key=None):
    k = key if key is not None else control_hmac_key()
    if not k:
        k = b"dev-hmac-unconfigured"     # ← 提交进仓库的公开常量
    return hmac.new(k, message.encode(), hashlib.sha256).hexdigest()
```
`jwt_secret=""`（`config.py:60`）、`control_hmac_key=""`（`config.py:235`，回退到 jwt_secret）—— **两者默认值都是空**。

**影响**：默认部署下（两个密钥均未配置）：

1. **审计哈希链完全失效** —— `audit_trail._compute_row_hash` 用这个公开常量签名，任何有数据库读权限的人都能为伪造的审计记录重算出合法哈希，"防篡改"承诺不成立
2. **审批票据签名可伪造** —— `human_approval.approve()` 校验的 `sig` 用同一密钥

更糟的是**测试也测不出来**：`tests/test_control_plane_security.py` 的 fixture 只固定 TTL，从不固定密钥，所以签名与验签双方都回退到同一个常量、结果一致，测试**永远绿**。

```python
def control_hmac_key() -> bytes:

    raw = (settings.control_hmac_key or "") or (settings.jwt_secret or "")
    if not raw:
        raise RuntimeError("control_hmac_key / jwt_secret 未配置：拒绝以公开默认密钥启动")
```

### P0-16 · 钓鱼检测全链路无 Unicode 归一，零宽字符即可完全绕过

**位置**：`backend/phishing_guard/email_detector.py`（全 12 文件）、`domain_detector.py:246-271`

### P0-23 · 嵌入服务故障时"零向量"被当作检索证据返回

**位置**：`backend/summary_compression.py:535`（已核验）；`backend/rag/retriever.py:76-81,293`

```python

logger.error(f"Embedding call failed after retries: {last_error}")

```
```python

min_score=0.0,
```

**影响**：`embed()` 吞掉失败并返回 768 个零，因此 `retriever.py:81` 的 `except → None` **永远不会触发**。零向量对 COSINE 集合而言与任意点的相似度都 ≈0；叠加 `min_score=0.0`，Qdrant 会返回**任意 top_k 个点**。这些 chunk 随后被 `_inject_exact_terms` 合并、通过 `_drop_unapproved`，并**以"安全知识库参考"的名义交给 LLM**。

即：**嵌入服务 2 分钟不可用 = 整个知识库退化为随机噪声，且被自信地标注为检索到的证据。**

pgvector 路径**不受影响**（`retriever.py:592-593` 计算 `score=1.0-distance≈0` 并过滤掉）—— 这正是为什么该缺陷只在**默认的混合检索配置**下发作。

**修复**：
```python
# retriever.retrieve 调用点
if query_embedding is not None and max(abs(x) for x in query_embedding) <= 1e-5:
    logger.error("[rag] query embedding 退化为零向量，跳过 dense 通道")
    query_embedding = None
```
并让 `embed()` 在失败时抛异常或返回 `None`（加 `strict: bool = True`），同时给混合路径设置真实下限。

### P0-24 · 检索到的 chunk 文本零分隔地进入提示词 → 检索投毒即判决投毒

### P0-25 · 文档入库写入未校验向量，且所有 chunk 共用同一 payload

**位置**：`backend/routers/rag.py:139-177`

```python
vec = await embedder.embed(chunk_data["content"][:1000])   # 失败即零向量，未校验
chunk = KnowledgeChunk(..., embedding=vec, ...)
...
await qdrant_store.upsert_chunk(..., payload={"content": content[:1500], ...})
                                          # ↑ 整篇文档的开头，而非 chunk_data["content"]
```

**影响**：两个独立缺陷：

1. **无零向量守卫**（对比 `seeder._backfill_runner:1125` **有** `_ZERO_EPS` 检查）。嵌入 API 不可用时，该文档的**所有** chunk 都以 `embedding=[0.0]*768` 落库并 upsert 到 Qdrant。知识库索引里塞满**互相全等的向量**，此后每次检索返回任意子集，且**无法区分被污染的 chunk 与正常 chunk**。
2. **payload 是文档头而非 chunk 文本** —— 同一篇文档的 N 个 chunk 写入**完全相同的 1500 字符**。`upsert_chunk` 由此派生 BM25 稀疏向量（`qdrant_store.py:157-159`），于是**同一文档的所有 chunk 获得完全相同的 BM25 向量**。混合 RRF 的词法通道**塌缩到文档级粒度**：无法区分 chunk 1 与 chunk 7，同胞 chunk 拿到相同稀疏分数与近似 RRF 排名 —— 整个 `rag_prefetch`/BM25 设计所依赖的精确词法匹配能力，**恰好在最需要它的多 chunk 文档（playbook、长 MITRE 技术）上失效**。

**修复**：
```python
payload={"content": chunk_data["content"][:1500], "title": title, ...}
# 写入前校验
if not vec or len(vec) != settings.embedding_dim or max(abs(x) for x in vec) <= 1e-5:
    raise HTTPException(503, "embedding 服务不可用，未写入向量")
```
已污染的 BM25 向量需用 `migrate_qdrant_hybrid.py` 回填修复。

## 4. 专项分析一：LLM 调用放大

**一条 P0 事件触发 10–35 次 LLM 调用**，且主导项由攻击者塑形：

| 阶段 | 位置 | 调用数 |
|---|---|---|
| Decomposer 预分析 | `agent_decomposer.py:335` | 1 |
| **SubAuditor（每 chunk 一次）** | `agent_executor.py:98,562-565`，chunk 上限 `MAX_CHUNK_EVENTS=20`（`chunker.py:21`），数据来自 limit=200 + limit=100 两次 `query_events` | **1–25** |
| schema 重试 | `sub_auditor.py:182` `MAX_RETRIES=1` | ×2 |
| EvidenceVerifier | `agent_executor.py:442` `claims_to_verify[:5]`，**逐条** `verify_batch` | 0–5 |
| deep_analyze / synthesize / recheck | `agent_executor.py:138,151,162` | 3 |
| Reviewer | `agent_reviewer.py:89`（deep 模式启用） | 1 |

其他车道：P1 `llm_single` = 1；P2/P3 = 0；流量型（DDOS/PORT_SCAN）短路为 `tools_only` = 0。

**主导项是 chunk 数，而它是攻击者塑形的**：攻击者只要在真实攻击落地前，从同一 `src_ip` 制造 200+ 条相关事件，就能把这一次 P0 审计的 SubAuditor 调用推到 10–25 次。叠加 P0-15（Temporal + 本地双跑）与 P1-2（activity 超时重跑），**同一事件可能把整组调用执行两遍**。

**同时存在的浪费**：
- `agent_reviewer.py:167` 的 `audit_json` 是**唯一无上限的提示词变量**，每轮深审都重传全部证据集
- `_verify_claims_with_knowledge` 逐条循环调 `verify_batch` 而非批量，最多 5 倍检索/嵌入开销
- `self_play.reviewer.drain` 每 900 秒**自动**运行且 `self_play_review_llm=True`，无进行中对局时也在烧 LLM
- 预算阶梯（P1-18）在默认配置下是死代码，**高消费时没有任何机制削减量**

## 5. 专项分析二：自博弈污染的完整链路

**默认部署（`self_play_inject=False`）是安全的，但靠的是一个布尔开关而非设计。**

开启后，仿真数据可触达的范围（无任何 flag 校验）：
1. `security_events` 与真实事件混合，**对所有读取路径和客户可见审计轨迹不可区分**
2. `_auto_create_case_bg` 创建**真实案例** → `case_auto_order_priorities=high,critical` 升级为**真实工单**并指派 admin
3. 通过门控的仿真攻击可触发**真实遏制**（防火墙 / 进程终止 / 主机隔离），目标 `10.0.30.x` **落在真实内网段内**，且不在 `protected_assets` 覆盖内
4. 进入 `audit_cache` 判决缓存，污染生产流量读取的同一 key 空间
5. 被 `learn_loop` 收割并自动应用阈值调优

**且与 `inject` 无关**：自博弈学到的规则通过 `engine.py:130` 加载 shadow 目录进入生产 Sigma 引擎，并每 900 秒自动晋升 —— **即使 `self_play_inject=False`，生产检测逻辑仍被污染**（见 P0-12）。

自博弈模块自身的卫生是**好的**，值得肯定：`SCORING_STATUSES` / `CANDIDATE_STATUSES` 分离（`overlay.py:13-14`）、`validate_rule` 要求 FPR < 0.05 且 ≥20 负样本、唯一正例时标记 `provisional`。**缺的是接入侧标记执行与晋升门控，不是评分模型。**

## 6. 做得好的部分（不要"修"这些）

- **`veto_gates.py` 是真实的程序化 fail-closed 实现**。`apply_confirmation_gate`（289-349）让 `confirmed` 在缺少非 LLM 检测器信号时**结构性不可达**；`merge_audit_rounds`（462-580）禁止跨轮 OR 合并并在无背书时把严重度压到中位数；`clamp_reviewer_conclusion`（655-665）让 Reviewer **结构上无法**高于 Executor。这不是"让 LLM 自我审查"。
- **Agent 轮次循环真有界**。`log_ingestion.py:814` 与 `workflows.py:50` 都是有限循环，另有 hop 预算与三重提前 break。**全链路无无界递归或 agent 循环。**
- **`SubAuditor` fail-closed**。`MAX_RETRIES=1` 硬上限、LLM 回退响应被识别且不重试、无 admitted claims 即 `threat_detected=False`、grounding 验证自身抛异常时回退到更严格的"剥离声明"路径。
- **`command_whitelist.py`** —— 锚定正则 + `GLOBAL_FORBIDDEN` 注入黑名单 + 默认拒绝 + 平台隔离 + 规则级 `forbidden` 二次校验。**全项目最干净的组件。**
- **`mcp_guard/call_record.py`** —— 剥离 `\x00-\x1f`/`\x7f`/`|`（日志注入防御）、深度 6 / 32 key / 32 元素封顶、4KB 参数上限与有界预览、NaN/Inf 归一、naive→UTC、**从不抛异常**。这是其他 logger 应该对照的参考实现。
- **`policy_engine.evaluate`** —— deny > require_confirmation > allow 优先级正确，命中 deny 即 break，CIDR 比较用 `ipaddress`（无字符串前缀 bug）。仅 `require_role` 分支写反（P1-20）。
- **`security_guard/intent_checker.THREAT_ACTION_MATRIX`** —— 真正 fail-closed：无法识别的威胁级别塌缩为 `"unknown"`，**只允许告警类动作**；矩阵外的动作名直接拒绝。
- **`field_cipher.py`** —— Fernet（随机 IV + 认证），密钥取自环境变量且从不落日志，密钥无效时**禁用功能**而非降级为弱实现。
- **`ja3_fingerprint.py` 的 JA3 部分** —— 字段选择、GREASE 剥离（完整 16 值）、MD5 用法均符合 Salesforce 规范。
- **`grounding_verifier.py:731-734`** —— 无知识库、无事件证据两种情况都返回 False，注释明确写了"单源 RAG 不得单独定罪"。
- **无灾难性回溯正则**。全部安全模块的 `re.compile` 都是有界字符类或字面量简单择一。真正的 CPU DoS 向量是算法性 Levenshtein 循环（P1-37），不是 ReDoS。
- **SQL 参数化在多数模块是正确的**。`ops.py:381-385`、`case_manager.py:534` 用 `text()` + `bindparams`；`rag/retriever.py:551-559` 的 jsonb 过滤用 `bindparams` 也正确。**唯一的例外是 `rag/knowledge_base.py:129-137`（P0-22）** —— 同样的 jsonb 过滤在那里用 f-string 拼接，说明是逐处遗漏而非约定缺失。

- **nginx 配置质量高** —— 完整安全响应头集、CSP、`server_tokens off`、Flink REST 收敛到 Basic Auth 反代（开源版 REST 无内置认证，原本直连会泄露集群配置）。

- **SQL 参数化、trace 上下文（W3C 严格校验）、schema_registry 保守 fail-open、metrics 低基数标签**均正确。
