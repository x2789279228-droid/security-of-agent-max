## 0. 为什么有第二轮

第一轮以安全为主轴。补扫后暴露的事实是：**这个项目"证明自己安全"的能力，比它"做到安全"的能力更弱。**

最尖锐的一条来自运维侧实测：`docs/security-audit/AUDIT_REPORT.md:15` 宣称"4-6 层防御"，其中点名的最外层 **Grounding 硬门控**（`grounding_verifier.py`，42 KB，全仓最大未测模块）在 101 个测试文件里**import 命中数为 0**，而它内部唯一那层策略还是 fail-open。评审方若追问"哪一层能拦下来"，答案只能是"靠 code review，不是靠测试"。

而这一切之所以长期没被发现，是因为**CI 门禁本身是红的**（15 个失败），红灯常态化之后就不再传达信息。

## 1. 测试质量：污染机制已定位到行（本次最有价值的发现）

全量实测 **15 failed / 882 passed / 3 skipped**（57.98s）。这不是"有些测试不稳"，而是**一个可精确定位的根因**。

### 1.1 根因：测试进程加载了开发者的真实 `.env` 【高】

`config.py:409-426` 的 `_load_project_root_env()` 在 **import 期**把根目录 `.env` 逐行灌进 `os.environ`（`if k not in os.environ`，425 行）。而 `conftest.py` 只用 `setdefault` 保护了 **5 个** `SHARED_MEMORY_*` 键，**其余 92 个键全部泄漏进测试进程**。

`.env` 里有 `RESPONSE_POLICIES_DIR=/data/response_policies` —— 一个 Linux 容器路径，在 Windows 上不存在：

```
PolicyEngine.__init__ (response_policies.py:415-417) 读该变量
  → 全局单例 policy_engine 指向不存在的目录
  → load_all() 返回空 → _load_source="code"
  → 日志：Taxonomy file missing: /data/response_policies/taxonomy.yml; empty index
```

**因果已双向证明**（同一批 7 个文件）：

| 条件 | 结果 |
|---|---|
| 保持 `.env` 原样 | **9 failed** |
| 仅把 `RESPONSE_POLICIES_DIR` 指向仓库真实目录 | **46 passed (2.30s)** |

这一个变量就造成了 **15 个失败中的 10 个**（threat_taxonomy×5、uncertain_containment×2、policy_yaml_reload、audit_endpoints、case_automation、case_lifecycle）。

**更危险的部分**（尚未造成事故，但已具备条件）：同样未被保护的有 `SHARED_MEMORY_FW_SSH_HOST/PASSWORD`、`QDRANT_URL`、`FIELD_ENCRYPTION_KEY`。`test_containment_host.py:75 test_live_no_ssh_unconfigured` 断言 `mode == "unconfigured"` —— **在一台配了真实防火墙口令的机器上，这条测试会尝试真实 SSH**。

**修复**：
```python

if os.environ.get("SHARED_MEMORY_SKIP_DOTENV") == "1":
    return
```

## 2. 运维就绪度：告警不存在，且流水线会自杀

### 2.1 Prometheus 只有 3 个抓取任务，零告警规则 【高】

`config/prometheus/prometheus.yml` 全文 25 行：`global` + 3 个 `scrape_configs`。全仓 `rule_files|alertmanager|alerting:` **零命中**。也没抓 postgres/redis/qdrant/kafka/temporal。

**审计流水线死亡时不会呼叫任何人。** 运维唯一的发现途径是有人恰好打开 Grafana。

### 2.2 健康监控与看门狗**一个指标都不发** 【高】

`health_monitor.py` 全文 import 的是 `logging`/`time`/`pipeline_tracer`，**没有 `metrics`**。告警路径只有三条：`event_bus.publish("pipeline_health")`（SSE，需有人开着页面）、`logger.warning`、回调 `watchdog.diagnose`。

**阈值、p95、卡死 span、冷却窗口全都写好了，就差一个出口。** 这是"投入很多、可运维性为零"。

### 2.3 Kafka 消费者自杀后永不重启 —— **项目自己的压测文档已记录，未修** 【高】

`docs/security-audit/attack-perf-large-scale-2026-09-10.md` 完整记录了故障链：

```
L19  Phase 2 入库 | 0 events drained to security_events  ← 核心问题
L266 平台"自爆"模式: 慢 → CommitFailedError → LeaveGroup → 永远不回来
L276 无 supervisor 重启
L313 平台今天的真实状态是"能接 HTTP 但没人处理"
```

代码现状核对属实：`enable_auto_commit=False` 但**无 `max_poll_interval_ms` 调优、无 `CommitFailedError` 捕获、无 rebalance listener**；`self._tasks` 只 `create_task`，**无 `done_callback`、无重启循环**。`CommitFailedError` 落到 `except Exception` → `finally: await consumer.stop()` → **协程结束，任务永久消亡**。8 个消费循环共用同一模式。

**一次 rebalance 就让整条 ingest 链路静默死亡，平台不会自己恢复。**

### 2.4 启动清扫把"卡住"改写成"已分析" 【高】

`app.py:316-347`（`stuck_auto_reset_minutes`，默认 30）：把最多 500 个 `analyzed=False` 的事件置为 `analyzed=True`，仅 `logger.warning`。

**而 2.3 的真实故障正是"事件入队但无人消费"。** 运维按 `deployment.md:103` 重启 backend 后，这条清扫把积压**改写成了成功**。数据永久丢失，运维看到 "Cleared 500 stuck unanalyzed events" 会以为积压已处理。

### 2.5 Kafka lag 探针用错误的消费组，数字恒等于 topic 全量 【高】

```python
consumer = AIOKafkaConsumer(group_id=f"{settings.kafka_consumer_group}-lag-probe", ...)
offset = await consumer.committed(tp)     # 从不提交的组 → 恒为 None → 恒为 0
```
真实消费组是 `f"{group}-{suffix}"`。结果 `total_lag` 恒等于 `end_offsets` 之和 = **topic 累积消息总数**。且只写内存 `self._stats["lag"]`，**无 Gauge**，超阈值仅 `logger.warning`。

**永远报警，且永远看不到真实积压。** 训练团队忽略它 → 真 lag 堆积也被一起忽略。

### 2.6 `/api/health` 在生产是无条件常量 【高】

```python
async def health():
    if _is_prod:
        return {"status": "ok"}      # 不接触任何依赖
```
数据库全挂时 Docker/K8s 仍判健康、LB 继续导流。CI 冒烟断言 `login in (200, 401)` —— **管理员口令完全错误也算通过**。

> ✅ 本轮已部分修复：新增 `GET /api/health/dependencies`（真实探测 postgres/redis/qdrant，LLM 给配置态）+ 前端 Monitor 接入。见 §6。

### 2.7 部署安全

- **3 个 Flink TaskManager 没有 `restart:`** —— 任一挂掉即永久消失，流处理静默降级到 1/3 容量
- **backend 无 healthcheck** —— "活着但卡死"的 backend 永不重启，LB 永不摘除
- 全仓仅 1 个 `deploy:` 键 —— **无 CPU/内存限制**
- `docker-compose.yml:581` `POSTGRES_PASSWORD: ${TEMPORAL_PASSWORD:-temporal_dev_pwd}` —— **硬编码默认口令**

## 3. 性能与容量

### 3.1 Sigma 检测每条事件 15 条同步 SQLite 语句跑在事件循环上 【高】

已逐行复核：

```python
engine.py:238  def detect(self, event: dict) -> list      # 同步函数，不是 async
engine.py:246  cols = list(ev.keys())                    # 表结构由【事件自身字段】决定
engine.py:249  # 每事件重建单行表，避免历史行残留造成假命中
engine.py:250  self._ensure_table(cols, ev)
engine.py:306  cur.execute(f"DROP TABLE IF EXISTS {self.TABLE}")
engine.py:310  cur.execute(f'CREATE TABLE {self.TABLE} ({coldef})')
engine.py:322  cur.execute(f'INSERT INTO {self.TABLE} ...')
engine.py:323  self._conn.commit()
engine.py:257  for meta, sql in self._compiled:          # 每条规则一次 SELECT
```

**DROP+CREATE 的意图（避免历史行假命中）用一条 `DELETE FROM events` 就能达成，代价是现在的 2 条 DDL。** 且列集合来自事件字段 —— 攻击者发带异常字段名的事件会让 `CREATE TABLE` 变宽。

12 ev/s 即 **180 条/秒阻塞整个 asyncio 循环**。`ingest_parallel_detect=True` 看着并发，但 `_run_sigma` 是同步的，`asyncio.gather` 对 sigma 那一半**零并行**。

### 3.2 LLM 槽内 3 次重试 × 90s read timeout = 270s 【高】

重试循环在 `limiter.acquire()` **内部**，`read=90.0` 恰等于整个 P0 预算，异常分支**无退避 sleep**。8 个挂起请求即可占满全部 8 槽 → 整条 P0 车道塌成纯规则。

### 3.3 其余要点

| 等级 | 发现 |

## 5. 架构与可维护性（量化）

### 5.1 890 处函数内延迟 import 掩盖了 7 个真实环 【高】

7 个环：`metrics↔event_bus`、`rag.retriever↔reranker`、`case_manager↔work_order_service`、`log_ingestion↔ingest_pipeline`、`audit_worker→log_ingestion→ingest_pipeline→audit_worker`、`pipeline_tracer↔stage_events`、`self_play↔orchestrator`。

**全部靠函数内 import 打破**，全仓只有 1 个 `TYPE_CHECKING` 守卫。后果：**"改 X 会破坏 Y 吗"必须读函数体而非 import 头** —— 这正是前几轮审计看不到这些接缝的原因。

### 5.2 171 个模块级单例，两个进程只接线了其中 4 个 【高】

`app.py` lifespan 手工接线 12+ 个单例（322 行）；`docker-compose.yml:475` 起**第二个进程** `temporal-worker`（同一镜像同一代码），只接了 **4 个**。它**从不调用** `cost_tracker.restore_today_usage()`（只在 `app.py:64`）。

**具体后果**：`CostTracker` 用进程内 dict，worker 从零开始 → `is_over_budget()` **对所有经 Temporal 路由的审计轮次静默低估** → 模块 docstring 承诺的"预算门禁不因重启失效"**跨进程不成立**。且 `app.py:52` 按 **UTC** 计算窗口，而 `CostTracker` 按 `date.today()`（本地）分桶 —— **UTC+8 下每天有 8 小时两者不一致**。

> **性价比最高的一条改动**：抽 `backend/wiring.py`，两处都调。约 60 行移动，纯搬移，风险低。

### 5.3 两个必知但不该现在动的结论

- **`models`(368 fan-in) / `config`(~105) 是不可避免的 hub** —— 正确做法是**门面式抽取**（`from models import X` 保持不变，零调用点改动），而非拆服务
- **"同进程分层，不拆微服务"这个决定今天仍然成立** —— 但代码库**已经存在一个未被管理的进程边界**（`app.py` ⟷ `temporal/worker.py`），靠复制粘贴维护，那才是真问题。唯一值得拆出去的是 NDR 抓包（需 `CAP_NET_RAW` 特权），但应在接线/可观测性修复**之后**做
