## 第一部分 · 先说清楚：这个平台现在的真实状态

### 1.1 一句话定位

一套端到端的安全运营平台（SOC）：**日志接入 → Kafka 流水线 → Flink 实时检测（规则 + 异常 + 攻击链）→ LLM 四层智能审计（被独立监督）→ 自动响应（默认 dry_run）→ 复盘/学习闭环**，全部 Docker 化，`docker compose --profile full up -d` 一键起。

### 1.2 规模数字（2026-10-27 全量对账口径）

| 维度 | 数字 | 说明 |
|---|---|---|
| 后端能力子模块 | 27 个 | rag/、sigma_engine/、response_engine/、mcp_guard/ 等 |
| REST 端点 | 231 个（19 个 Router） | 最大的是 ops.py（63 个运营端点） |
| 后端测试 | 3084 项（252 个文件） | 含 Kafka+PG testcontainers 集成测试 |
| 数据库表 | 52 张（models.py） | init.sql 里另有 29 张基础表 |
| Flink 作业 | 6 个（3 核心 + 3 NDR/EDR 扩展） | Java 11，CEP + DataStream API |
| Kafka Topic | 16 个 | 分区数/保留策略在 tools/init-kafka-topics.sh |
| Docker 服务 | 34 个（9 个 profile 分档） | full/lite/edge/ndr/intel/sandbox/rerank/firewall |

### 1.3 能力状态：哪些是"真的"，哪些是"实验性的"

**这是全项目最重要的诚实机制**：`backend/capabilities.yaml` 是唯一事实源（18 项能力，三档制），前端 `/sensing?t=capabilities` 和 `/api/capabilities` 直接读它。

| 档位 | 数量 | 能力 | 含义 |
|---|---|---|---|
| **verified** | 4 | ingest_kafka、ingest_normalization、case_workorder、observability | 有真实数据回放证据，可信 |
| **experimental** | 13 | flink_validation、audit_pipeline、response_engine、rag、self_play、mcp_guard、threat_intel、ndr、tls_fingerprint、edr、phishing、temporal、behavior_anomaly | 代码完整、测试齐全，但**缺真实数据集验证或真机演练** |
| **disabled** | 1 | zeroday | 默认关闭（依赖外部 CAPE 沙箱） |

> **答辩要点**：不要把 18 项能力都说成"完成了"。评委问"哪个能力你最敢打包票"，答案是 ingest_normalization（对抗保持率 1.0、误报 0）和 observability。说得出"experimental 的差距具体差在哪个证据上"（比如 audit_pipeline 缺 50 条人工标注基准），比说"都完成了"更加分。

### 1.4 检测能力的真实数字（docs/benchmark/，全部可复现）

| 评测 | 结果 | 你的解读 |
|---|---|---|
| CSIC-2010 全量回放（61065 条真实 HTTP 日志） | 签名子集召回 **0.347**，全类召回 **0.029**，误报 **0/36000** | 召回不高是**如实测量**的结果——SigMA 规则覆盖面有限；FP=0 是硬门禁（宁可漏报不误报）。这个取舍本身是考点 |
| 对抗保持率（8 攻击家族 × 4 编码混淆） | **0.438 → 1.0**（规范化改造后） | 证明"攻击者换编码绕过规则"这条规则僵化短板被修复 |
| Sigma 吞吐（150 规则） | **~34 eps**（每事件秒级毫秒数 42ms/事件） | 已知性能断点：单进程 Python 消费侧 ~23.5 eps 就饱和。生产要扩容——知道瓶颈在哪比数字本身重要 |
| 异常检测在真实流量上 | 100% `inconclusive`（基线样本不足不出结论） | 刻意设计：证据不足就拒绝下结论（fail-closed 思想延伸到 ML），不是缺陷 |
| 审计分流 | ~76% 事件走规则收口，只有高危进 LLM | 成本控制的经典手法：规则兜底 + LLM 只看难的 |

### 1.5 已知短板（审计报告的诚实账本）

2026-10-21 全量审计（docs/AUDIT-2026-10-21-全量代码审计报告.md）发现的三类系统性落差，**补课时每一类都值得你亲自看一遍**：

1. **休眠模块**：代码在、测试在，但生产代码没人 import（= 从未真正运行过）。审计时发现 21 个，经两轮接线后 README 登记剩 7 个（如 mitm_proxy、peer_group、llm_correlation）。有 `test_dormant_modules_guard.py` 守卫：一旦接线，测试转红提醒收口。
2. **历史 P0 未清零**：10-03 审计的 25 个 P0 仍有 4 个未修。
3. **故障路径"永不丢事件"三处不成立**：如响应异常被吞但 Kafka offset 仍提交（静默丢失）——这是分布式系统最经典的坑。

> **给你的话**：这套"审计 → P0 清单 → 修复 → 守卫测试锁住"的流程，本身就是大学里很少教、工业界极度看重的工程能力。看懂这些报告 = 学会了怎么对一个大系统做质量问责。

### 1.6 一条日志的一生（知识地图的骨架）

后面所有知识点都挂在这条链上，建议背下来：

```
日志源(syslog/API/EDR/NDR/钓鱼)
  │ API Key / SASL_SSL 认证
  ▼
Kafka security-logs-raw
  ▼
Flink LogValidationJob ──── schema校验·API Key白名单·60s去重 ──→ rejected/duplicate(审计)
  ▼ validated
Flink AnomalyDetectionJob ─ 异常评分(Welford基线) + CEP攻击链(3模式)
  ├→ security-alerts          (score≥0.6 或 high/critical → 响应引擎)
  └→ security-audit-queue     (score≥0.3 → LLM 审计)
Backend ingest_worker:
  ├ pySigma 单事件命中 ──→ security-sigma-hit ──→ Flink 阈值聚合 ──→ alerts
  ├ 异常检测五维加权 → correlation_engine 攻击链关联 → IOC 富化
  ▼
Audit-LLM 四层流水线 (Temporal 编排)
  Decomposer → ToolBuilder → Executor(并行工具+SubAuditor) → Reviewer
  ↑ 全程被 CAD 独立监督(穿透验证+上下文审计+熔断器)
  ↑ 5 道闸: Grounding验证 · Faithfulness Gate · Veto Gates · Stabilizer · LLM Fallback
  ▼
响应引擎: 策略匹配 → [高危→人工审批] → SafeExecutor(6层检查) → dry_run/mock/live → 回滚TTL
  ▼
EventStore + 记忆树 (PG + Qdrant) → 案例沉淀 · 工单 · 复盘 · 反馈回灌规则 · 红蓝自博弈
```

## 第七部分 · 怎么和 AI 协作学习，而不是被 AI 代劳

你缺的不是文档，是"亲手碰壁"的机会。以下是可以立刻执行的操作规则：

1. **读代码让 AI 提问，不让 AI 总结。** 把一个文件丢给 AI："基于这个文件向我提 10 个问题，从我答不上来的难度开始。"答错的地方才值得它解释。
2. **让 AI 只给提示，不给代码。** 做第五部分任务时加一句："不要给我代码，只告诉我该看哪个函数、关键障碍是什么。"
3. **费曼检验。** 每学完一个模块，用自己的话向 AI 复述设计，然后命令它："从这段话里找出所有技术错误和含糊之处。"它挑出的每一个错都是你的知识漏洞。
4. **改造优先于阅读。** 永远先有一个要动手改的任务，再带着任务去读代码——纯阅读的留存率极低。
5. **用 git log 当教案。** `git log --oneline` 里每个 commit 都是一次真实决策（如 `8c0849f chore(guards): 接线成功后的守卫收口`）。挑 20 个 commit，用 `git show <hash>` 看完整 diff，问 AI"这个改动在防什么问题"。这比任何教程都真实。
6. **允许自己"先用后懂"。** AI 帮你产出的东西不丢人，但给每样东西立一张"欠条"（TODO 卡），12 周计划就是还债的时间表。
