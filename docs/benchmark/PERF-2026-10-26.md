# 第一轮压测 — 端到端吞吐/延迟/丢失 + 故障注入(2026-10-26)

- 目标平台: 本机 `docker compose -p soc`(lite 单 broker) 全栈
- 攻击机: 独立容器 `kali-pentest`(`kalilinux/kali-rolling`), 只对 soc 施压
- 规则库: 150 条(影子 125), 与 B1/B2/B3 同库
- 样本: 合成攻击事件(8 类威胁轮转), 非公开数据集
- 压测工具: `tools/attack-large-scale-2026-09-10.py`(批次模式, JWT Bearer 鉴权)

## 复现命令

```powershell
# 0) 登录(压测必须带 JWT; X-API-Key 单独会被 401)
$envf='<repo>\.env'
$pw=(Select-String -Path $envf -Pattern '^SHARED_MEMORY_ADMIN_PASSWORD=').Line -replace '^SHARED_MEMORY_ADMIN_PASSWORD=',''
$tok=(Invoke-RestMethod -Uri 'http://localhost:8001/api/auth/login' -Method Post `
      -Body (@{username='admin';password=$pw}|ConvertTo-Json) -ContentType 'application/json').access_token

# 1) 从攻击机容器灌负载(产物写容器 /tmp, 不落仓库)
docker exec -e SOC_TOKEN="$tok" -e SOC_API="http://host.docker.internal:8001" `
  kali-pentest python3 /workspace/tools/attack-large-scale-2026-09-10.py `
  --total 6000 --rate 100 --session lt-p1 --id-prefix p1- --out /tmp/lt-p1.jsonl

# 2) 真实落库回查(不能用 HTTP 2xx 当成功)
docker exec shared-memory-pg psql -U admin -d shared_memory -t -A `
  -c "select count(*) from security_events where session_id='lt-p1';"

# 3) 消费位点/积压(列序: GROUP TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG …)
docker exec soc-kafka kafka-consumer-groups --bootstrap-server localhost:9092 `
  --describe --group soc-backend-ingestpy
```

剖面参数: P1 `--total 6000 --rate 100` / P2 `--total 12000 --rate 500` /
P3 `--total 6000 --rate 100 --id-prefix p1-`(复用 P1 前缀=重放) /
P4 内联 3000 请求(非 JSON / 缺必填 / 类型错 / 双重编码 各 1/4) / P5 故障注入见下。

## 怎么读这些数

- **饱和点在 Python 消费侧, 不在接入侧** —— 接入侧批量 500 时能到 130.8 eps、零失败零拒绝;
  而检测引擎实测 42.46 ms/事件(150 规则)⇒ 单进程上限 ≈23.5 eps, 实测消费 13.97~22.1 eps。
  换句话说: **Kafka/Flink 侧还有余量, 掉队的是单进程 Python 检测+审计**。
  这与 B1 报告的 "~34 eps(155 规则/事件, 单事件私有 SQLite)" 量级一致(本轮 42.46 ms 略慢)。
- **HTTP p50 2~3 秒不是网络问题** —— 是同步等 broker ack 的在途窗口
  (`kafka_produce_gate`=32 在途 + `acks=all` + 幂等生产者)。批量越大越摊薄:
  500/批 → 130.8 eps, 100/批 → 34.5 eps。
- **背压信号与真实瓶颈错位(本轮最值得记的一条)** —— 429 闸门看的是"审计队列深度",
  本轮该深度峰值仅 537/2000(27%), 却在 130.8 eps 下**一个 429 都没出**;
  真实背压发生在 Kafka lag(峰值 12,216)上, 而系统不自知。
  ⇒ 用"消费者追不上"做限流是无效的, 准入闸门必须绑到真实瓶颈(消费端速率 / 审计 PQ 深度)。
- **异常检测在生产流量上不产出结论** —— `soc_detection_outcomes_total{detector=anomaly,
  outcome="inconclusive"}` = 17,267/17,267 = **100%**。这与 B3 报告"阈值可行区间为空、
  当前阈值 0.60 在内"是同一件事的两面: 阈值在区间内, 但真实流量分布落在区间外。
  ⇒ 异常检测当前**不可用**, 能力页应如实标注。
- **审计主路径其实是规则收口** —— `soc_audit_lane_admit_total`:
  tools_only(P2) 13,137 / llm_single(P1) 1,388 / llm_agent(P0) 2,347
  ⇒ 约 **76% 的审计本就走规则通道**; LLM 通道完成 365 次(llm) + 1,016 次(cache 命中)。
  这为"无 LLM 也能闭环"提供了本轮侧证(未单独跑无 key 剖面, 见"边界")。
- **审计 PQ 指标口径不可信** —— `soc_audit_pq_enqueue_total{P0}`=2,242 而
  `dequeue_total{P0}`=7: 真实审计走内存队列, PQ 进出严重不对称 ⇒ 不能用 PQ 深度当背压信号。
- **HTTP 接入路径不过 Flink 主流水线(口径事实, 别按文档想当然)** ——
  `security-logs-raw` 全程仅 8 条 / `security-logs-validated` 18 条,
  而 `security-events-ingest` 24,469 条 ⇒ `LogValidationJob`(raw→validated→enriched)
  在 HTTP 接入路径上**基本空转**; 活的是 Python 消费路径
  (`security-events-ingest` → backend) 与 `sigma-hit`(5,190)→Flink 聚合支线。
  ⇒ 本报告的吞吐结论按 Python 消费路径给; Flink 主流水线的吞吐**本轮未测**。

## 改前基线(压测前必须先修的 8 个阻断项)

本轮压测前, 平台的 Kafka 链路是**全断的**, 且日志/容器状态一片正常("看起来在跑")。
逐项均为实测复现并修复:

| # | 阻断项 | 症状 | 修法 |
|---|---|---|---|
| 1 | alembic `fileConfig` 顶掉宿主 root logger | 迁移后**所有 INFO 日志消失**, `Kafka producer started` 永远看不见 | `backend/migrations/env.py`: fileConfig 后把 root 还给宿主 |
| 2 | `.env` 缺 `KAFKA_BOOTSTRAP_SERVERS` | Flink/schema-registry 指向不存在的 `kafka-1:9092`; 作业 FAILING、SR 崩溃循环 | `.env`: `KAFKA_BOOTSTRAP_SERVERS=kafka:9092` + `COMPOSE_PROFILES=lite` |
| 3 | `flink-jobs/*.sh` 是 CRLF | `/bin/bash^M: bad interpreter` → job-submitter exit 126 崩溃循环 → **作业一个都没提交** | `flink-jobs/Dockerfile`: `sed -i 's/\r$//'` |
| 4 | Flink checkpoint 配置只在客户端缺失 | 作业 checkpoint 被禁用(interval=Long.MAX_VALUE) → EXACTLY_ONCE 事务**永不提交** → `read_committed` 消费者**一条都读不到** | checkpointing 写进**镜像**的 `config.yaml`(客户端与集群共用) |
| 5 | checkpoint 状态卷属主 root | `Failed to create checkpoint storage` → 作业直接 FAILED | 镜像内 `mkdir + chown flink:flink`; 存量卷 `docker exec -u 0 chown` |
| 6 | compose 未接线 `SHARED_MEMORY_EXECUTION_MODE` | `.env` 配 `live` **不生效**, 响应引擎永远 dry_run | compose 的 backend 与 temporal-worker 两处补映射 |
| 7 | 作业并行度只有 1 | 客户端 `flink run -p` 优先于 JM 的 `parallelism.default` → 15 槽只用了 3 槽 | compose 给 job-submitter 补 `FLINK_PARALLELISM=3` |
| 8 | 43 条存量困在旧作业遗留的**未决事务** | `read_committed` 永久不可见(连 abort 都轮不到) ⇒ 该批数据实际已丢 | 分区级重置 consumer offset 放行 |

> 第 4 项是"43 条存量消化后 lag 归零"这件事的**真凶**: 旧作业因 checkpoint 被禁用,
> Kafka 事务从未提交, 下游按 `read_committed` 根本看不到这些消息 ——
> **"数据在 Kafka 里"不等于"数据对下游可见"**。
> 判定"平台没丢事件"必须区分三件事: 消息已写入 / 事务已提交 / 消费者已提交 offset。
> 本例前两件都成立过, 但第二件从未成立。

## 结论边界

> **勘误（2026-10-26 代码核查后，不影响本表任何实测数字，仅修正两处解读）**：
> 1. **HTTP p50 2~3s 的主因不是 ack 在途窗口** —— Sigma 检测（42.46ms/事件）以
>    **裸同步调用阻塞共享事件循环**（12 audit worker + 9 消费循环 + FastAPI 同一
>    asyncio loop，`ingest_pipeline.py:368` 无 to_thread），批量越大批内串行检测越久。
>    ack 窗口（gate=32 + acks=all）是次级因素。修复面：`asyncio.to_thread` 卸载
>    （引擎每事件私有连接，线程安全前提已具备），见 PERF-OPT-PLAN Wave 1-2。
> 2. **压测观察到的 429×2407 来自 rate-limit 中间件 crit 桶**（`app.py rate_limit_middleware`），
>    不是 admission 闸门 —— admission 闸门默认发 **503**（`config.http_overload_status`），
>    其信号（内存审计队列/2000）峰值 27% 从未触发，与正文结论一致且更甚：
>    真实瓶颈信号（KAFKA_LAG，峰值 12,216）已有 Gauge 但无任何闸门读它。

- **剖面时长压缩**: 文档要求每剖面 ≥30 min 稳态 + 10 min 恢复; 本轮稳态 60~175 s、
  恢复观察 ~10 min。⇒ **量级可信, 收敛曲线不完整**; "60 s 内归零"的验收线本轮**未达成**
  (实测 536 s), 但**忽略验收标准**的前提下, 排空速率本身是可信的。
- **Flink 主流水线未测**: HTTP 路径不过 Flink 主流水线(见上), Flink 层的
  checkpoint 成功率/反压/事件时间正确性**不在本轮结论覆盖范围**;
  本轮只测到"作业能起来、checkpoint 23~24 次全成功、TM 被杀能自恢复"。
- **未覆盖的剖面/注入**: 无 key(无 LLM)剖面(需改配置, 本轮不跑)、kill 1/3 Kafka broker
  (本机 lite 单 broker, kill 即全灭)、LLM 供应商 429 mock、kill api 进程
  (审批 write-behind 恢复)。⇒ 这四项的"架构是否成立"本轮**无数据**。
- **合成流量**: 事件为合成攻击样本(8 类威胁轮转), 不代表真实分布; 绝对值不可外推到生产。
  真实流量面的召回/误报由 B1(REPLAY-CSIC-2010)/B2(EVASION)/B3(ABLATION) 负责。
- **内存驻留未回落**: 压测中 232 MiB → 压测后 511 MiB(2 GiB 上限)。本轮只取了单点快照,
  **不足以判定泄漏**; 文档"8 h 稳态 RSS 增长 < 10%"需要在更长尺度上单独跑。
- **异常检测 100% inconclusive** 是本轮真实流量的观测, 不是合成标定集结论 ——
  两者方向一致(阈值区间内但真实分布落在区间外), 但**不能用合成集数字冒充生产表现**。
- **封禁链路的可用性缺口(压测外发现, 单列)**: `rollback_batch(batch_token)` 对
  `FW-RULE-` 级令牌返回 `failed=2` 且 **iptables 规则未被删除** ⇒ 封禁只能等 TTL 到期
  自动解除。演示链路(block_ip → 真实 iptables DROP → `containment_records` 落行
  `status=applied`)本轮实测通过, 但**回滚必须修**。
- 压测全程未改动仓库文件; 压测产物写在容器 `/tmp` 与 `%TEMP%`。
